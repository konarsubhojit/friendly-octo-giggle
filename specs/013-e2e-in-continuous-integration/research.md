## Decision 1 — Database in CI

**Decision**: Provision Postgres and a Neon WebSocket proxy as GitHub Actions `services:`, apply the committed migrations with `drizzle-kit`, load a committed seed, and reach the database through the existing data access layer via a CI-only `neonConfig` branch in `src/lib/db.ts` gated on a new optional `E2E_WS_PROXY` environment variable.

Concretely:

- `postgres:16-alpine` service, network alias `postgres`, host port `5432`, `pg_isready` health check.
- `ghcr.io/neondatabase/wsproxy:latest` service with `APPEND_PORT=postgres:5432` and `ALLOW_ADDR_REGEX=.*`, host port `5433` mapped to container `80`.
- `DATABASE_URL` points at `localhost:5432` and is used unchanged by `drizzle-kit migrate`, by the seed, and by the application (R8).
- `E2E_WS_PROXY=localhost:5433/v1`. When set, `src/lib/db.ts` assigns `neonConfig.wsProxy` (function form, per R3), `neonConfig.useSecureWebSocket = false`, and `neonConfig.pipelineConnect = false` before constructing the pools. When unset, nothing is assigned.

**Rationale**: This is the only option that satisfies FR-014 ("reach that database through its existing data access layer without altering production behavior") and FR-010/SC-008 (no secret, so fork pull requests run the same blocking set) simultaneously. It is verified end to end by R7, R8, R9, and R10 rather than assumed. The CI branch is provably inert in production: the variable exists in no deployment environment, it is declared `optional()` in the Zod schema so a stray value cannot silently change types, and a Vitest case asserts the `neonConfig` fields keep their defaults when the variable is absent. Migrations need no proxy at all (R9), so the schema application path is identical to the one `database-migrations-preview` already uses.

**Alternatives considered**:

| Alternative                                                                             | Why rejected                                                                                                                                                                                                                                                                                                                                                                                                                 |
| --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Hosted ephemeral Neon branch created per pull request                                   | Requires a Neon API token as a repository secret. Secrets are not exposed to `pull_request` runs from forks, so the blocking set would be skipped or fail on fork pull requests — a direct violation of FR-010 and SC-008. Also adds an external service to the critical path of every merge, and Principle IV's "no server-managed state" argument does not extend to making merges depend on a third party's availability. |
| Swap `src/lib/db.ts` to `drizzle-orm/node-postgres` in CI                               | Changes the driver under test, so CI would exercise a code path that never runs in production. FR-014 forbids altering production behavior, and Principle III's "tests must fail when behavior breaks" is undermined if the transport differs from the deployed one.                                                                                                                                                         |
| Bare `postgres:16` service with no proxy                                                | Verified impossible (R2). The driver performs a WebSocket upgrade against the Postgres port and the connection is refused at the protocol level. `src/lib/env.ts` throws at import, so this fails at boot, before any route renders, and Playwright route interception cannot rescue it because Server Component reads never cross the browser network boundary.                                                             |
| Add `neonConfig` overrides in a Playwright global-setup file instead of `src/lib/db.ts` | The application server is a separate process from the Playwright runner. Configuration set in the runner has no effect on the server that renders the pages.                                                                                                                                                                                                                                                                 |
| `pg-gateway` or a hand-written WebSocket shim                                           | More code to own for the same result the vendor's own proxy image already delivers. Principle VII.                                                                                                                                                                                                                                                                                                                           |

## Decision 2 — Serving a production build to the browser

**Decision**: Run `next start` on `http://localhost:3000` and suppress the HTTPS redirect for the CI run with a second CI-only environment gate, `E2E_ALLOW_INSECURE_HTTP`, read in `src/proxy.ts` alongside the existing `NODE_ENV` check. `PLAYWRIGHT_BASE_URL=http://localhost:3000` selects the CI mode; the unset default keeps the local `https://localhost:3000` dev behavior (`playwright.config.ts:6`).

**Rationale**: R11 through R14 close off every alternative that leaves the redirect active. Injecting `x-forwarded-proto: https` looks attractive and fails for two independent reasons: the `webServer` readiness probe cannot carry headers and follows the 301 into a dead port (R13), and Next.js derives `initURL` from that header, so `request.nextUrl.clone()` in the three `src/proxy.ts` auth redirects emits absolute `https://localhost:3000/...` locations that the browser cannot reach (R14). `session-isolation.spec.ts` walks exactly those redirects, so this is not a corner case.

The concession is narrow and its blast radius in the deployed topology is nil: the redirect only fires when `x-forwarded-proto` is absent or `http`, and the deployed edge always sets it to `https`, so the branch is already unreachable in production. Suppressing it inside a job whose server binds to loopback and whose database holds only fixtures removes no real protection. Session security is unaffected — R15 proves Chromium still stores and returns the `__Secure-` cookie over loopback, and R16 confirms the production cookie name is what gets exercised.

The gate is inert by construction: `E2E_ALLOW_INSECURE_HTTP` is declared `z.enum(['true','false']).optional()` in `src/lib/validations/env.ts`, defaults to absent, and a Vitest case asserts the 301 still fires when it is unset.

**Alternatives considered**:

| Alternative                                                                    | Why rejected                                                                                                                                                                                                                                                                                  |
| ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| TLS terminator sidecar in front of `next start`                                | Roughly 60 lines of committed transport code, a per-job `openssl` certificate, a second port, and a new npm script — all to obtain TLS on loopback, which carries no security value in an ephemeral job. R15 already removed the cookie argument that would have justified it. Principle VII. |
| `x-forwarded-proto: https` via `use.extraHTTPHeaders`                          | Disqualified by R13 and R14. It would also have needed the header replicated by hand on the three manually constructed contexts (`global-setup.ts:41`, `session-isolation.spec.ts:83-87` and `:134-138`), since `extraHTTPHeaders` does not reach `browser.newContext()`.                     |
| Run the CI server with `next dev`                                              | FR-002 requires a production build. `next dev` does not exercise the Cache Components prerender path that `session-isolation.spec.ts` guards, which is the Principle IV obligation this feature inherits from `012`.                                                                          |
| Probe a redirect-exempt route (`/robots.txt`, `/sitemap.xml`) and keep the 301 | Fixes only the readiness probe. Every subsequent page navigation still hits the 301, so it does not address R14 at all.                                                                                                                                                                       |

## Decision 3 — Sharding and merged reporting

**Decision**: Four shards via Playwright's own `--shard=k/4`, each emitting a `blob` reporter output, merged by a single downstream job with `npx playwright merge-reports --reporter html`. The blocking lane runs `npm run test:e2e -- --shard=${{ matrix.shard }}/4` so CI invokes the same documented command as a contributor (FR-017).

**Rationale**: R19 shows `--shard` distributes whole `(project, file)` groups and balances by case count, which is exactly what the spec's Q3 asks for and needs no bespoke partitioning table to maintain. The measured baseline assignment over the 14 blocking projects was 56 / 43 / 52 / 39 cases before repair, and the repair removes the two 18-case `ux-audit` groups that currently unbalance shards 2 and 3. R19 also fixes the floor: `admin-views.spec.ts` at 25 cases is indivisible, so no shard count below the point where one shard carries only that group buys anything. Four shards puts the busiest shard at roughly 25 to 40 cases.

Reporting must be merged because a per-shard HTML report is four partial reports and SC-007 asks for downloadable failure artifacts for the run, not for a shard. The `blob` reporter is Playwright's supported input to `merge-reports` and needs no extra dependency.

**Alternatives considered**: Eight shards — rejected, per-shard fixed overhead (checkout, `npm ci`, browser restore, migrate, seed, server boot) is roughly 3 to 4 minutes and would come to dominate; the 25-case floor means the marginal shard saves nothing. Manual `--project` groups pinned per shard — rejected, it hard-codes a balance that rots the moment a spec file grows, and it makes the CI command diverge from the documented one, against FR-017. A single unsharded job — rejected, the ceiling case (every test consuming its full timeout) exceeds the 15-minute budget.

## Decision 4 — Browser binary caching

**Decision**: Cache `~/.cache/ms-playwright` with `actions/cache@v6` keyed `${{ runner.os }}-playwright-${{ steps.pw.outputs.version }}`, where the version is read from `node_modules/@playwright/test/package.json` at run time. Install only Chromium. On a cache hit run `npx playwright install-deps chromium`; on a miss run `npx playwright install --with-deps chromium`.

**Rationale**: FR-004 requires the key to be the Playwright version, and reading it from the installed package rather than from `package.json`'s `^1.62.0` range makes the key track what is actually installed. R21 establishes that Chromium alone covers all 17 live projects, which removes the Firefox and WebKit downloads entirely. Splitting `install-deps` from `install` is required because the cache restores browser binaries but not the apt-level system libraries, which live outside the cached path. A cache miss then costs a download, not a failure, satisfying the spec's edge case that a miss must slow the job rather than fail it.

**Alternatives considered**: Keying on `hashFiles('package-lock.json')` — rejected, it invalidates on every unrelated dependency change and does not satisfy FR-004's wording. Committing browsers or using a prebuilt container image — rejected as disproportionate machinery for a cache that restores in seconds.

## Decision 5 — Artifact strategy

**Decision**: Enable `trace: 'retain-on-failure'` in `playwright.config.ts` (R20 shows traces are currently `off`, so SC-007 cannot be met without this). Each shard uploads its `blob-report` directory; the merge job uploads the merged HTML report plus the `test-results` directory containing traces and failure screenshots. Retention is 14 days for reports and traces. Uploads run with `if: always()` so a failing shard still publishes evidence.

**Rationale**: SC-007 requires a trace per failed test, which is only produced when tracing is enabled. `screenshot: 'only-on-failure'` is already set (`playwright.config.ts:35`), so failure screenshots land in `test-results` without further change. Fourteen days is the "bounded retention period" FR-005 asks for and comfortably outlives a review cycle without accumulating storage the way the 90-day default does. `video: 'off'` stays off — traces already carry screenshots per action, and video would multiply artifact size for no additional diagnostic value.

**Alternatives considered**: `trace: 'on'` — rejected, it traces every passing test and inflates both runtime and artifact size. `trace: 'on-first-retry'` — rejected because Decision 8 sets retries to zero, which would leave every failure untraced. Ninety-day retention — rejected, unbounded in spirit and unnecessary.

## Decision 6 — Advisory lane

**Decision**: A separate `e2e-advisory` job running the three advisory projects with `continue-on-error: true` at job level. It uploads its artifacts with the same `if: always()` pattern and is **not** listed in the required check's `needs:`.

**Rationale**: `continue-on-error: true` marks the job neutral rather than failed, so the workflow conclusion stays green while the job still executes every test, publishes its report, and shows its own red or green box in the checks list. That satisfies FR-018's three requirements — still executes on every run, still publishes artifacts — without the workflow turning red. Making the required check independent of it is what keeps an advisory failure from gating merge.

The two tracked reasons and promotion conditions:

| Advisory project                  | Tracked reason                                                                                                                                                                                                                                                                       | Promotion condition                                                                                                                                                                     |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `desktop-chrome`, `mobile-chrome` | `ux-audit.spec.ts` combines a layout-overflow heuristic (`:108-112`) with unconditional full-page screenshot capture (`:116-119`). The heuristic depends on font metrics and viewport rounding, and the screenshots have no baseline to compare against — out of scope per the spec. | Promote when the overflow assertion is expressed against a stable, enumerated set of elements rather than a live DOM query, and the screenshot capture is separated from the assertion. |
| `orders-live`                     | R23: hardcodes product id `tprod01`, which no committed seed provides, and gates five assertions behind visibility checks that log instead of failing.                                                                                                                               | Promote when the product identifier is discovered at run time the way `product-navigation.spec.ts` does, and every conditional branch either asserts or fails.                          |

**Alternatives considered**: `continue-on-error` at step level — rejected, the job would still be marked successful in a way that hides which step failed. A separate workflow file — rejected, it duplicates the whole database and server setup for three projects and puts the advisory result on a different check surface, which makes FR-018's "publish its artifacts" harder to find. Deleting the advisory projects — explicitly forbidden by FR-018.

## Decision 7 — Fixture seed placement and determinism

**Decision**: `scripts/seed-e2e-fixtures.mjs`, plain ESM, run with `node` after `drizzle-kit migrate`. It imports table definitions from `src/lib/schema.ts` and hashes the test account password with `bcryptjs` directly at cost 12. All catalog identifiers are fixed 7-character Base62 literals. The script is idempotent: it deletes its own rows by known id before inserting.

**Rationale**: R25 rules out importing `hashPassword` from `src/features/auth/services/password.ts`, because that module pulls in `primaryDrizzleDb` and would construct the Neon pool as a side effect of seeding — before the proxy configuration is relevant and for no reason. Calling `bcryptjs` directly with the same cost produces a self-describing hash that `compare` accepts unchanged, so the divergence is in the call site only, not in the artifact. Importing `src/lib/schema.ts` is safe (R25) and is what keeps the seed in lockstep with `drizzle/`: a column the migrations add and the seed must fill becomes a type error rather than a runtime surprise.

Deterministic literal ids are a deliberate, recorded divergence from the `generateShortId()` rule: that helper is random by design (`src/lib/short-id.ts`), and a seed whose ids change per run cannot back a deterministic suite. The literals conform to the same `varchar(7)` Base62 shape the column enforces. `User.id` and `Account.id` are `text` with a `crypto.randomUUID()` default, which the coding standard already exempts as auth tables.

`.mjs` follows the `scripts/apply-idempotent-bootstrap.mjs` precedent and avoids a TypeScript execution step in the middle of the CI critical path. R26 requires the `/* eslint-disable no-console */` header that both existing scripts already carry.

**Alternatives considered**: A SQL file under `scripts/sql/` — rejected, it duplicates schema knowledge that would drift from `drizzle/` silently. Seeding through the application's own API routes — rejected, it requires the server to be up before the data exists, which inverts the dependency and cannot create an admin account. A Playwright `globalSetup` seed — rejected, four shards would race on the same database.

## Decision 8 — Retries

**Decision**: `retries: 0` in the blocking lane. Flaky tests are quarantined into the advisory lane with a tracked issue, per the spec's User Story 3.

**Rationale**: SC-003 requires ten consecutive runs to produce identical results. Retries make that criterion unmeasurable — a suite that retries twice reports "identical results" while masking a one-in-three failure rate. The spec is explicit that a test failing intermittently is quarantined rather than left to erode the signal, and retries are precisely the mechanism that erodes it. This is also what makes `trace: 'retain-on-failure'` the correct trace setting rather than `on-first-retry` (Decision 5).

**Alternatives considered**: `retries: 2`, the common CI default — rejected, it contradicts SC-003 and the spec's quarantine rule. The cost is accepted: a genuine infrastructure blip turns a pull request red and needs a manual re-run, which is the intended pressure toward fixing the underlying instability.

## Decision 9 — Reusing the build artifact

**Decision**: The existing `build` job gains an upload of `.next` (excluding `.next/cache`) as a short-retention artifact. The end-to-end jobs declare `needs: [build]`, download it, run `npm ci`, and start `next start`.

**Rationale**: FR-003 requires the job to depend on a successful build and not run when the build fails, which `needs: [build]` delivers with one edge and no extra job. Rebuilding inside each of the five end-to-end jobs would add roughly four minutes each and put four jobs in a race over the same `.next/cache` key. Reuse is safe because the values the CI run needs at run time are read at run time, not inlined: `src/lib/env.ts` parses a spread of `process.env`, so `env.NEXT_PUBLIC_APP_URL` and `env.NEXTAUTH_SECRET` are runtime reads. The one genuine build-time inline is `src/app/sitemap.ts:13`, which references `process.env.NEXT_PUBLIC_APP_URL` directly; no blocking project asserts on the sitemap, and the fallback it uses is already `http://localhost:3000`.

**Alternatives considered**: A dedicated `e2e-build` job — rejected, an extra node in the graph for a build the `build` job already produces. Rebuilding per shard — rejected on time budget and cache contention. Uploading `.next/cache` too — rejected, it multiplies artifact size for a directory `next start` never reads.

## Decision 10 — Keeping the admin UX audit alive after the project split

**Decision**: Move the admin route audit onto the advisory projects by changing `ux-audit.spec.ts:11` so `ADMIN_PROJECTS` resolves to `desktop-chrome` and `mobile-chrome`, and wrap the admin `describe` block in `test.use({ storageState: AUTH_STATE_PATH })`.

**Rationale**: The spec's Q4 forbids a project mixing blocking and advisory spec files, so `**/ux-audit.spec.ts` must leave `admin-desktop` (`playwright.config.ts:107`) and `admin-mobile` (`:117`). R22 shows the spec file gates its admin cases on those exact project names, so removing the pattern without touching the file would silently retire seven admin route audits — which FR-018 forbids.
